## 1. 基本原则

- **清楚、整洁、好用。** 按真实需要组织项目，不为形式增加文件、层次和审批。
- **中文为主。** 标题、正文、图示和用户提示用简体中文；代码、命令、路径、字段及品牌名保留原文。
- **一事一处。** 同一事实只维护一份正文，其他位置用短摘要和链接。
- **按需展开。** 必填栏目保留，可选内容按条件加入；不建空目录，不虚构事实。
- **持续收敛。** 每个工作包同步受影响的代码、说明和引用，不等项目结束。
- **尊重现场。** 沿用有效结构和生态约定，保护用户改动。

“工作包”是一组产生可检查结果的工作，包含必要实现、验证和说明更新。一次性问答、只读检查和小修改不自动初始化项目。

## 2. 架构、代码与目录

### 2.1 设计与实现

- 按职责划分入口、核心规则和外部接入；小脚本可以用函数区分，不必分文件。
- 先满足已确认需求。近期扩展有依据时再预留，不为假想需求搭框架。
- 按职责与维护需要拆分，不按行数、文件数或 AI 上下文长度拆分，也不合并无关内容。
- 共用逻辑确有共同含义、能降低维护成本时再提取，允许尚未形成共性的少量重复。
- 遵循语言的命名、格式、类型和错误处理约定；失败可定位，注释解释理由和边界。
- 新增重要能力、职责/依赖变化或重构前，在受影响路径和已知入口有界查既有实现、调用者与测试，说明复用、扩展或新建理由及查找边界；未找到不等于不存在。普通小修不扩大为全仓考古。
- 明确受影响模块负责/不负责什么及允许依赖；有意例外说明理由，不强制统一目录树或预建空框架。重构先明确保留行为，再以相关回归保护，不以更少文件/行数代替质量。

需要时在现有设计中讲清下列内容；无法简洁承载或需要独立维护时再拆文件：

| 涉及内容 | 说明重点 |
| --- | --- |
| 接口与跨模块调用 | 输入、输出、错误与兼容 |
| 持久数据 | 读写责任、保留与迁移 |
| 并发与后台任务 | 生命周期、取消、超时、重复执行与一致性 |
| 运行版本与配置 | 生效方式、失败影响、恢复与验证 |
| 重要取舍 | 选择、理由和代价；需要独立追溯时使用 ADR（架构决策记录） |

### 2.2 目录与命名

- 根目录能找到使用入口，不额外套 `source-版本-提交号/`。
- 目录按职责建立；单脚本可留根目录，需要打包、导入或独立维护时再用 `src/` 等生态布局。
- 前后端、服务和共享模块确需独立维护时再分目录，不预建空层次。
- 区分源码、安装内容、运行数据和恢复点；版本隔离放在需要它的安装或构建位置。
- Swift Cycle 可写任务必须建立/复用项目根 tmp/，Git 默认忽略 /tmp/；可控临时材料集中于此，系统临时目录仅作工具受限例外，按第 9 节处理。
- 索引在查找困难时增加；不因整理自动迁移已有稳定路径。
- 重要能力的文件落点依据现有职责、调用关系和生态选择；在既有 DESIGN/SAD 补受影响的“能力 → 实现 → 调用入口 → 测试 → 既有证据”定位，暂无项如实标明，证据只链接，不建第二套状态/功能账本或全函数登记。

| 对象 | 命名 |
| --- | --- |
| 新项目 | 多词用下划线，品牌及大小写遵循组织约定 |
| 根级固定文档 | `README.md`、`AGENTS.md`、`DESIGN.md`、`TODO.md`、`DEVLOG.md` |
| 新普通 docs 文件和多词目录 | 小写 snake_case；目录索引可用 `README.md` |
| 固定专业文档名例外 | `PRD.md`、`SAD.md`、`BLUEPRINT.md`、`ROADMAP.md`、`MANUAL.md`；保留准确大小写 |
| 里程碑计划 | `docs/milestones/M1_PLAN.md`、`M2_PLAN.md`；编号稳定 |
| 代码、测试、锁文件、技能入口 | 沿用语言、框架和工具约定 |
| 图及长期说明 | 按用途命名，原位更新，不堆日期副本或 `new`、`old`、`final2` |

`SKILL.md` 是技能入口，参考、脚本和模板按需分置，开发材料不全量进入安装包。图源与导出图沿用现有资源位置，无图不建图片目录。

## 3. 文档分工与引用

以下路径相对仓库根，先按目录层级、再按同层文件名 A–Z 排序。持续项目按条件建立文档；已有等价来源就复用，不机械创建整套文件。

| 文件 | 维护内容 | 建立条件 |
| --- | --- | --- |
| `AGENTS.md` | Agent 的环境、执行、授权和验证规则 | 采用项目执行规则时 |
| `DESIGN.md` | 概要设计、UML 结构、功能/接口/数据与交付形态、实现位置及详细文档导读 | 有设计内容时 |
| `DEVLOG.md` | 紧凑条目保留有用的维护结论与理由，记录多时按真实里程碑分组 | 获准创建/正式初始化必需；无结论如实说明 |
| `README.md` | 面向用户的用途、安装、使用和求助 | 持续维护项目默认具备 |
| `TODO.md` | 当前进度、里程碑位置与差距、待办/问题、阻塞和下一阶段 | 获准创建/正式初始化必需；后续按已确认记录策略维护 |
| `docs/BLUEPRINT.md` | 项目蓝图：目标、愿景、用户、场景、核心能力和产品边界 | 新建持续项目；旧项目复用等价说明 |
| `docs/MANUAL.md` | 可操作环境的前提、启动/停止、验证、回滚和排障；README 保留首次使用入口 | 存在运行边界且操作说明确需独立维护时；不推导运行授权 |
| `docs/PRD.md` | 已确认且仍有效的需求、行为边界和验收条件 | 持续迭代项目默认具备；一次性任务可复用已有需求来源 |
| `docs/ROADMAP.md` | 阶段结果、依赖、顺序和完成判断 | 跨工作包安排需要独立维护时 |
| `docs/SAD.md` | 详细结构、协作与关键机制 | 简洁 DESIGN 已不足以承载时 |
| `docs/milestones/M{N}_PLAN.md` | 一个里程碑的工作包、实施与验证 | 顺序、影响或独立审阅需要详细计划时 |

BLUEPRINT 提供项目目标、愿景、用户、场景、核心能力和产品边界，蓝图构想不等于实现承诺。DESIGN/SAD 引用 PRD 的确认需求与约束；ROADMAP 安排这些需求的阶段结果；编号计划引用需求、设计和对应阶段；TODO 定位当前工作包。引用使用实际文件链接，需要定位具体条目时再加稳定编号。

项目目标、用户、核心场景、能力边界或关键约束实质变化时更新 BLUEPRINT；其他变更按表中职责同步受影响文档。DESIGN 解释详细文件回答什么、如何关联、何时阅读，不仅列文件名。SAD 与 MANUAL 仅按实际需要独立维护，ADR 保留重要架构决策的背景、备选和后果；由 DESIGN 导航，文档多到影响查找时再加 docs 总索引。

docs 首页与 ADR 索引按实际查找需要直接组织说明和链接，不提供固定模板，不因存在目录就新建 README、状态表或修订账本；独立 ADR 决策提纲仍按已采用的决策约定使用，命名与适用边界见统一规约。

同一里程碑只维护一份现行计划。TODO 不复制计划，DEVLOG 不复制行动清单或发布历史。验证栏目链接已有结果，不另写重复报告。

使用 Swift Cycle 获准创建项目或正式初始化时，根级 TODO.md、DEVLOG.md 必须有效交付，是初始化完成条件；缺失或无效不得报告完成。创建属于初始化授权，不逐文件再请批；已有有效文件原样保留，只补缺失文件，不重置或迁移。

新 Git 项目默认精确忽略 `/TODO.md`、`/DEVLOG.md` 并验证未跟踪；已有明确策略保留。非 Git 项目仍须双文件，Git 跟踪/忽略检查不适用，不擅自 `git init`。只读咨询、普通维护、仅采用不推定初始化授权，不自动补建本地记录或改其 ignore。内容无效、权限或策略冲突明确未完成，不擅自覆盖、改权限或取消跟踪；集中操作边界见 [本地记录与初始化预检](../skills/swift-cycle/references/document-profiles.md#本地记录与初始化预检)。根级 tmp/ 是独立的可写任务约定，见第 9 节。

本 Skill 的文档职责、模板、命名导航、能力复用、本地记录和有界回收统一由 [项目结构与文档规约](../skills/swift-cycle/references/document-profiles.md) 按六章承载，入口按任务定位相应章节，不维护分离的组织规约正文。合并仅收敛来源，不改变初始化、重构保全或资产回收授权边界，也不增加消费者文档要求。

参考按任务分工：文档选择与格式看 document-profiles，更新触发看 lifecycle-and-closeout，表达与图示操作看 zh-CN；采用、治理和工具衔接分别看对应参考。入口保留关键条件与链接，完整规则只维护一处；保留六份文件、统一规约的六章及两张表，普通术语用中文，技术标识保持原文。

## 4. 固定模板

### 4.1 共用写法

- 一篇文档一个中文一级标题；固定栏目用二级标题，名称与顺序保留，通常只细分到三级。
- 新建或整体重整使用模板，小修改只更新受影响部分；已批准的等价结构不强行改名。
- 必填栏目可简写，无事项写“暂无”；可选内容按条件省略，未知不能写成“不适用”。
- 写具体对象、动作和结果，先结论后理由；一段一个重点，步骤用列表，比较用表格，复杂关系用图。
- 术语首次解释后统一称呼，不堆缩写、宣传词和中英同义双写；区分设想、示例、实现与验证。
- 标题、正文、列表、表格和代码块之间留空行，核心前提、步骤和限制不折叠。
- BLUEPRINT、PRD、DESIGN 和 SAD 首页简写状态与更新日期；确需区分版本或范围时再补。

| 避免 | 改写 |
| --- | --- |
| 完成全链路闭环 | 安装、播放和恢复分别通过了哪些检查 |
| 高扩展性架构 | 增加一种输入格式只需修改读取模块 |
| runtime gate fail-closed | 兼容检查失败时停止启用 |
| 已验证，应该没问题 | 本地测试通过，目标设备尚未验证 |

一级标题使用“项目名＋用途”，README 只用项目名。用途依次为：项目蓝图、产品需求文档、概要设计、软件架构文档、项目执行规则、产品路线图、里程碑 N 实施计划：结果名称。TODO／DEVLOG 用“项目进度与 TODO”“维护记录”；可选 MANUAL 使用“操作与运维手册”。

本章固定模板已逐项确认，专业提纲仍是候选。表中每行对应一个二级栏目。

以下均为同一虚构“清单检查工具”的教学样例。默认起点：需求 R1、R2 已确认，M1 待实施，API 仅是候选。涉及阶段推进的示例另注明时点；示例命令、设计和结果不代表本地实现或验证。

### 4.2 README.md：用户入口

默认采用[README 展示模板](../skills/swift-cycle/templates/README.md)：居中项目名、一句话用途、少量真实徽章与稳定锚点导航，按需放实际预览图；影响使用的状态与限制显著展示。二/三级标题各带一个语义相关 Emoji；六项核心职责及顺序不变，不将图标样式强加给 TODO 等其他文档。小改动仍保护已有有效结构，用户明确风格要求优先。

| 必填栏目 | 填写要求 | 简写样例 |
| --- | --- | --- |
| ✨ 用途与适用范围 | 使用者、用途、适用环境及关键边界；用短句与能力表 | 帮助维护者检查指定目录的缺失文件，只读取，不自动补齐。 |
| 🧰 准备条件 | 用户真正需要的环境、账户和材料；仅保留适用表格行 | 需要 PowerShell 7、可读目录和清单。 |
| 🚀 安装或接入 | 推荐入口、执行位置、步骤和成功判断；可复制代码块 | 交付时在根目录提供入口与帮助命令；当前尚未实现。 |
| 🎬 第一次使用 | 准备输入、执行任务、检查结果；配实际截图或输出 | 对示例目录运行检查；应报告预设缺失项，输入文件保持不变。 |
| 🛠️ 日常使用与求助 | 常用操作表、常见问题及真实反馈入口 | 更换目录或清单后重新检查；权限不足时核对读取权限。 |
| 📄 限制与许可 | 已知限制、未验证范围及许可来源 | 只读检查；许可尚未确定，当前不对外分发。 |

**按需增补：** 权限与凭据放“准备条件”，多端入口放“安装或接入”，接口、目录和技术栈参考放“日常使用与求助”，不强制创建。涉及配置、更新或撤销安装时，在“限制与许可”前依次增加“⚙️ 配置与数据”“🔄 更新与迁移”“⏸️ 暂停、恢复与卸载”。公开 GitHub 仓库可加“⭐ Star History”，必须是全文最后一节；非公开或非 Git 项目删除该节与不适用徽章。

**展示与填充：** 使用 Markdown 和受支持的少量 HTML，不依赖任意 CSS/JavaScript；图片须真实净化，CLI/库/Skill可用实际输入输出替代图片。填实全部 `{{变量}}`，保留准确技术标识和目标文档语言；无真实图片、Release、许可文件或文档时移除相应链接，不留失效占位或虚假状态。可折叠替代安装方式/FAQ，但不折叠必需操作与关键限制。不生成贡献和免责声明栏目；这不取消真实限制、未验证范围或许可来源说明。模板中的目标项目路径变量不是 Skill 自身依赖，实例化后须核真实链接/图片与导航锚点。

许可正文使用真实许可状态，文件链接仅在有实际来源时保留；无许可文件时删除许可徽章和文件入口，正文明确实际状态，尚未确定则如实说明，具体回退写法由 README 模板给出。

### 4.3 docs/BLUEPRINT.md：项目蓝图

| 必填栏目 | 填写要求 | 简写样例 |
| --- | --- | --- |
| 产品愿景 | 希望谁的处境发生什么改变 | 让维护者迅速确认材料是否齐全，减少逐项翻目录。 |
| 目标用户与问题 | 使用者、现有做法和困扰 | 维护者目前人工核对清单，容易漏项。 |
| 核心使用场景 | 情境、任务、体验和结果 | 接手一份材料时，选择目录与清单，得到可读的缺失项。 |
| 产品形态与核心能力 | 用户入口、主要能力；区分已有与构想 | 设想以命令行为入口，读取清单、比较目录、展示差异。 |
| 范围与非目标 | 产品边界及不承担的相邻职责 | 检查所选目录；不下载、补齐或删除材料。 |
| 目标结果与成功标准 | 产品价值怎样判断 | 交接时能直接定位缺项，减少逐项翻目录。 |
| 关键约束与待决问题 | 影响方向的条件、假设和问题 | 当前面向 Windows 命令行；对外接口（API）尚未纳入需求。 |

复杂用户旅程配体验图；收费或成本影响项目成立时补商业目标。技术模块、操作步骤和排期放在对应文档。

### 4.4 docs/PRD.md：产品需求文档

| 必填栏目 | 填写要求 | 简写样例 |
| --- | --- | --- |
| 目标与场景 | 谁在什么情境遇到什么问题，希望得到什么结果；简写依据 | 维护者交接资料，用清单检查指定目录；依据愿景的交接场景。 |
| 范围与非目标 | 确认的能力边界、不承担事项与必要取舍 | 单目录、单清单检查；不扫描其他目录，不自动补齐或删除。 |
| 需求与验收 | 具体行为、可观察的通过条件与重要失败行为 | 见下方 R1、R2。 |
| 约束与质量 | 适用环境、兼容、性能、安全或数据要求及判断办法 | Windows、PowerShell 7；UTF-8 清单每行一个文件名；检查前后输入内容不变。 |
| 待确认事项 | 未定问题、影响及确认办法；没有写“暂无” | 是否需 CSV 导出？先明确用途、字段与优先级，当前不实施。 |

需求确认不等于立即排期。需求写行为与验收，设计写办法，计划写任务。已实现且仍有效的需求继续保留；进度放计划，验证结果引用已有结论。

**按需增补：** 有跨文档引用时加稳定编号，需要取舍时补优先级与短理由。质量栏目只写适用要求；多角色、分支或状态难讲清时配图，界面行为难讲清时配原型。独立领域确需分别维护时再拆文件，不并存多份等价需求文档。

**需求表简例：**

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| R1 | 列出清单中缺失的文件 | 输出与预设缺失项一致；齐全时显示“无缺失” |
| R2 | 读取失败时说明原因 | 清单不可读或目录无权限时明确报错，不返回“无缺失” |

**新需求接收：** 明确问题、预期行为和验收条件，核对对当前工作、依赖与设计的影响，建议加入、替换或后移。未定想法留在待确认事项，确认后进入需求正文，选入当前工作时再调整安排。已有决定就同步；目标、范围实质变化或优先级冲突时集中请用户决定。

| 情况 | 处理 |
| --- | --- |
| 原需求的澄清 | 范围未变，补准确表述与验收条件 |
| 原要求未满足 | 按缺陷修正，保留原标准；旧完成判断有误则纠正 |
| 新增或改变能力 | 更新需求，确定取舍后调整受影响阶段与工作包 |
| 已完成阶段后的新需求 | 安排后续工作包；形成独立阶段结果时才新增里程碑 |

例如 M1 已完成只读检查，随后确认 CSV 导出为 R3：补充需求及验收条件，再安排后续工作，不把 M1 改成未完成。路线图保留当时完成范围；旧计划的过程可收敛，必要结论与固定引用保留。

需求变更按第 3 节分工同步，编号保持稳定，不另建变更流水账。

### 4.5 DESIGN.md：概要设计

| 代码与目录组织 | text 代码块的目录树、行尾职责注释、关键入口及共用能力定位 | 用树枝显示实际层级；单脚本用简短树，只维护受影响导航。 |

| 设计文档导读 | 详细文件回答什么、如何关联、何时阅读 | 本页足够时如实说明，不新建空详细说明。 |

使用[概要设计模板](../skills/swift-cycle/templates/DESIGN.md)，不使用 Emoji。新建或获准整体重整时至少交付一张对应实际项目的 UML 结构图，默认组件图说明模块、接口与依赖；明确现行/拟议部分，原稿和导出图随设计同步。架构类 UML 沿用 Figma 可编辑节点/文字/连线及 PNG/SVG 导出，工具或授权不可用时标明未完成，占位文字不算图；普通小改不自动补绘或重整旧文档。

多模块协作按需补时序图/活动图，重要生命周期可用状态图，对象关系复杂可补类图，多节点运行可补部署图；不机械凑齐全部图种。非架构类图按语义使用 Mermaid、PlantUML 或既有工具。小项目仍可用简洁组件关系，不虚构类、前后端、数据库或服务；没有接口/持久数据/部署环节如实简写，不新建空文档或目录。

正文保持概要层次，不展开逐函数实现或安装运维步骤。详细机制、既有决策和验证依据在相关位置摘要并链接；取消旧三个固定栏目不取消必要设计判断、验证与事实边界，也不将其复制为新的流水栏目。

“代码与目录组织”采用 `text` 代码块的树状展示，用 `├──`、`└──`、`│` 表示层级，行尾 `#` 注释职责，不使用目录表格。替换示意名称为实际主要目录/关键文件，拟议项明确标注，不列全量文件；重复内容可用 `...` 省略。树形排版不规定物理布局，不据此建目录；树只描述文件落点，不能替代 UML 的组成、接口与依赖关系。

仅在新增重要能力、职责/依赖变化或重构时补受影响部分：整体结构说明负责/不负责事项、允许依赖及例外；代码组织说明有界查找与复用/扩展/新建理由、落点及“能力 → 实现 → 调用入口 → 测试 → 既有证据”定位。重构仍须明确保留行为及相关回归，证据只链接，不新增固定栏目或第二套功能状态账本。

### 4.11 DEVLOG.md：维护记录

采用[紧凑条目模板](../skills/swift-cycle/templates/DEVLOG.md)：一级标题“维护记录”，二级标题“有效维护记录”；默认用“日期｜主题”的加粗列表条目，单条不加子标题或固定多字段，不使用 Emoji。结论与理由为核心，验证、适用条件、未知和后续影响按需补。

```markdown
# 维护记录

## 有效维护记录

- **2026-10-13｜暂不拆分多层目录**
  当前只需一个脚本，用函数区分职责；增加独立入口或模块后再拆，避免多余跳转。
```

条目多到影响查找时，在“有效维护记录”内按真实里程碑增加三级分组，组内仍用紧凑条目；不预建空未来组，无里程碑不强设编号或路线图。没有新经验就不新增条目；无记录时写“当前无新增维护结论”。同一问题的多次调查原位提炼，保留重要拒绝理由、适用条件、未知和固定证据；重要结论变化保留形成时的边界并补变化说明。正式事实进入对应共享说明，本地只留经验与链接；经验影响当前工作时同步 TODO，不记录逐命令、逐批准或逐对话历史。

获准初始化仍必须交付 DEVLOG 文件，填写实际有效结论及理由，或如实写明无新增维护结论；“无经验不新增条目”不等于可以缺文件。已有有效文件原样保留，不编造经验、不覆盖空壳或占位内容来假造通过；无效内容列为未完成及必要处置。

## 9. 持续收敛与清理

正文去重与引用修正属于正常维护；文件回收另核对授权对象、使用情况和恢复价值。

采用、接管、初始化和后续可写任务开始时，必须在已确认项目根创建/复用 tmp/，保留已有内容并核对真实路径未越界；Git 默认精确忽略 /tmp/，已有有效规则不重复，不为跟踪空目录添加 .gitkeep。非 Git 同样建立目录，不为此 git init。只读任务只核对缺口，不创建目录或改 ignore。同名文件、重定向、已有跟踪内容、不可写或策略冲突保留现场，不覆盖、不取消跟踪或改权限；采用/初始化完成须同时核对目录和适用忽略状态，未满足明确未完成。

可控草稿、一次性脚本、fixture、下载暂存和检查中间输出统一放根级 tmp/，优先用工具目录参数，必要时仅对子进程设置 TEMP/TMP/TMPDIR 并核实际路径，结束后恢复，尽量减少额外 C 盘写入。工具必须用系统临时位置或路径不可控时说明实际位置和原因；不为此修改用户/系统级环境、全局缓存或其他项目，不搬迁既有缓存、不扫描清理 C 盘。正式资产和持久运行数据保持原职责位置，tmp/ 不授予自动清空或删除权限。详细落地规则由[项目根临时目录](../skills/swift-cycle/references/document-profiles.md#项目根临时目录)维护。

| 材料 | 处理 |
| --- | --- |
| 当前源码、补丁、构建配方、锁文件、必要测试 | 保留，退役前核对依赖 |
| 缓存、中间输出、一次性脚本 | 可重建、无人使用且不承担恢复时列为回收候选 |
| 安装内容、加载库、用户数据、恢复点 | 按使用和恢复需要保留 |
| 旧报告、计划、实验材料 | 提炼必要结论与理由，不保留无用过程 |
| 秘密、本地配置、私人材料 | 按项目边界保护，不进入公开源码 |
| 固定合同引用的材料 | 保留路径与身份，按合同处理变更 |

`build/`、`artifacts/` 的名称不决定去留；用途、使用者、许可和生命周期一致时才合并。闲置扫描只是线索，没有代码引用不等于无人使用。

回收前核对目标路径、使用者和恢复材料；目录、符号链接与 ReparsePoint 要检查边界。Windows 用回收站，其他环境用已核对的可恢复方式；仍在使用、机制不明或路径越界则保留，不永久删除或清空回收站。

旧过程不搬进 history 或 ZIP。长期事实更新对应说明，本地只留当前行动和有效经验；必要未知、重要拒绝理由及固定引用不能丢。Git 历史不能代替本地忽略文件、用户数据和运行恢复点。
